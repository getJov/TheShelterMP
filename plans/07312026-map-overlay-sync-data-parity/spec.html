Why

After the Leaflet → Google Maps migration, every custom layer (lot canvas, block chrome, site-plan images, cluster chips) is glued to the viewport in container-pixel space but mounted inside (or beside) map surfaces that Google translates and scales during gestures. Result: overlays keep their old size for a beat when zooming, get cut off while panning, and the Map Editor can freeze a stale lot canvas in the wrong place — which reads as "the editor loads different data than the park map".

What

One shared pane-anchored canvas primitive that all map layers render through, in div-pixel space (self-consistent under Google's pane transforms at every frame), plus view-event–driven redraws. Same primitive used by Park Map and Map Editor so both stay in lock-step with the base map during pan and zoom. Editor drafts additionally re-hydrate from the live dataset whenever they are clean, so both screens always show the same published data.

Done means: no visible desync between base map and overlays during drag or wheel zoom on either page beyond the sub-frame Google itself allows; the editor never shows a misplaced/stale lot layer; a clean editor draft always equals the live dataset.

Context

Root causes found

  • src/features/map/lot-canvas.ts — canvas appended to the overlayMouseTarget pane at left/top: 0 but drawn in container pixels; draw() only repaints when React pushed props (_dirty), so map-driven draw() calls (pan re-anchor, zoom) show stale bitmaps. Park Map self-heals via hover-driven prop pushes; the editor passes noop handlers, so it freezes misaligned.
  • src/features/map/google/image-overlay.ts — site-plan image positioned against the map container div on bounds_changed; no events fire during the zoom animation → image keeps its old size, then snaps.
  • src/features/map-editor/chrome-canvas.ts — blocks/preview drawn on a screen-fixed canvas from bounds_changed; same zoom-animation gap, one-frame pan lag.
  • src/features/map/BlockClusterLayer.tsx — pane children positioned with container pixels inside draw(); only correct at re-anchor moments.
  • src/features/map-editor/store.ts hydrate() — keeps a clean (non-dirty) draft forever once loaded; dataset mutations elsewhere (sales, approvals) never reach the editor until reload.

Key invariant this build exploits

Content positioned and drawn in div-pixel space inside a map pane is correct by construction at all times: during a drag Google translates the pane (content rides along), during the wheel-zoom animation Google scales the pane (content tracks the ground), and at each re-anchor the API calls draw() where we re-position and repaint. Container-pixel space is only valid at the instant of an event.

Patterns To Follow

  • Imperative layer classes owned by thin React shells (LotCanvasLayer.tsx pattern) — no per-lot React nodes.
  • Typed-array projection buffers and grouped fills stay exactly as in lot-canvas.ts.
  • Theme colours only via colors.ts helpers.

Reference file: src/features/map/lot-canvas.ts — closest analog for the new primitive's overlay lifecycle.

Constraints

Must

  • Keep public APIs of LotCanvas, createImageOverlay, ChromeCanvas stable so React shells stay untouched where possible.
  • Redraws rAF-coalesced; full lot repaint stays ≈1–2 ms (verify with ?debug=perf).
  • Hover/click hit-testing keeps working on Park Map (tooltip coordinates relative to the map container).

Must Not

  • No new dependencies; no WebGLOverlayView (vector-only — satellite raster is the product default).
  • No behaviour change to editor tools' pointer math (container-space hit paths stay).
  • No touching the in-flight migration's unrelated files.

Out Of Scope

  • Editor DOM handles (rotation/resize chips, SVG bits) keep useMapTick container positioning — sub-frame lag on chrome accepted for now.
  • Persisting editor drafts across reloads.
  • Dirty-draft merge/conflict UX (dirty drafts intentionally keep priority over live data until published/discarded).

Assumptions (-i self-resolved)

  • The dirty working tree is the same in-flight Google Maps migration this fixes; work layers on top of it, nothing stashed, nothing committed unless asked.
  • “Load the same data” = clean drafts must track the live dataset (version-aware re-hydrate); the stale-canvas illusion is fixed by the rendering work.

Risk

Level: 2 — hot-path rendering rewrite used by both map screens.

Risks Identified

  • Regression in hit-testing/tooltips after coordinate-space change. Mitigation: hit-test stays canvas-local (rect-derived, scale-corrected); pointer events report map-container coordinates; browser walkthrough covers hover/click.
  • Pane z-ordering differs from previous DOM order (images move from map div into overlayLayer pane). Mitigation: lots render in overlayMouseTarget (above), images in overlayLayer (below) — same visual stack as today; per-overlay z-index preserved among siblings.
  • Re-hydrate could clobber an in-progress draft. Mitigation: dirty drafts never re-hydrate; version check only refreshes clean drafts; publish records the post-publish version.

Blast radius: MapCanvas + EditorCanvas (via LotCanvasLayer), SitePlanOverlay, DraftOverlayLayer, EditorSurface (via ChromeCanvas), BlockClusterLayer, MapEditorPage, editor store.ts consumers (helpers.ts report/validation read draft state — untouched fields). QA scripts qa/*.mjs exercise both pages.

Pushback

  • Perfect per-frame sync during Google's zoom animation is impossible for viewport-fixed DOM on raster maps — the public API exposes no per-frame camera. The pane-anchored approach is the same mechanism Google's own GroundOverlay/vector shapes use, which is the best achievable; do not chase WebGL for this.

Why

The map editor is becoming a core operational feature, not a developer-only geometry tool. Admins need a layered visual editor that aligns a cemetery layout against a mock/base map and site-plan reference while preserving inventory identity.

The current editor has useful primitives, but the admin mental model must be simpler: map at the bottom, site plan above it, blocks inside the site plan, lots inside blocks, and tier sizing as real-world lot dimensions.

What

Implement a rectangle-first layered layout system in /map-editor. The initial scope supports mock/base map controls, site-plan overlay alignment, rectangle blocks, rectangular lots, real-world tier sizes, mode-based editing, draft-only changes, conflict warnings, and Publish blocking for invalid layouts.

Done means an admin can align the visual cemetery layout, create and resize rectangle blocks, generate placeholder available lots from rows/columns/count, arrange lots within a block, edit tiers by individual selection, multi-select, or paintbrush-style assignment, and publish only after overlap and outside-block conflicts are resolved.

Guided Flow Continuation

The layer system must present as a guided cemetery layout setup flow, not a technical toolbox. The default sidebar leads admins through progressive steps with plain-language labels: Map reference, Site plan, Blocks, Lots, Tiers, and Review.

Advanced tools remain available, but hidden by default behind an expandable Advanced tools section. Base map and Review are view-only steps; direct map alignment handles appear only when the active setup step can actually be moved, resized, or rotated.

When a block is resized, the Grid/Lot layout step must provide a clear Rearrange existing lots action. This action reflows the current lot records onto the planned rows and columns without changing lot ids, lot numbers, block assignment, tier, status, client, contract, burial, notes, or capacity. If the current grid has fewer slots than existing lots, the action must explain that rows, columns, exact count, or block size must be adjusted first.

Baseline Source Of Truth

  • Layer order: mock/base map, site-plan overlay, blocks, lots, labels/status/tier overlays.
  • Geometry scope: rectangle blocks and rectangular lots only. Arbitrary block polygons, freeform lots, warped site-plan images, and geospatial calibration are later work.
  • Base map scope: mock/base map is acceptable. No Google Maps integration and no real geospatial map-canvas rotation in this execution.
  • View versus data: pan, zoom, satellite/default, and reset north affect the view/reference layer only. Rotating the view must not mutate cemetery geometry.
  • Site plan: uploaded or existing site-plan image remains a visual reference layer. Admin can move, resize, rotate, set opacity, show/hide, and lock it in draft.
  • Blocks: blocks are rectangle containers for now. Admin can move, resize width, resize height, rotate, and set row/column/count generation parameters.
  • Lots: lots are rectangular inventory shapes inside exactly one block. Lots may be moved visually only within their current block during normal layout editing.
  • Sold or occupied lots: admins may move them visually inside the same block, but their lot ID, lot number, block assignment, tier, status, client, contract, payment, burial, capacity, notes, and price relationship must remain unchanged unless a separate explicit action allows that field change.
  • Cross-block movement: dragging cannot move a lot into another block. Cross-block movement requires a separate confirmable reassignment action and must keep protected-lot safeguards.
  • Placeholder lots: grid generation creates available placeholder lots automatically. Admin can control rows, columns, and exact lot count manually. Reducing count may remove only available placeholder lots unless explicitly confirmed by an inventory action.
  • Existing-lot rearrangement: a block-local rearrange action must move the existing lot records onto the current planned grid slots. It must preserve identity and business fields, including sold/occupied lots, and block when the plan has fewer slots than the existing lot count.
  • Tier dimensions: tier widthM and lengthM are authoritative real-world dimensions. The app stores dimensions in meters; any feet display is conversion-only.
  • Tier catalog boundary: tier definitions still belong to Pricing/Lot Types. Editing a tier's dimensions must not silently rewrite published lot polygons outside the map-editor draft workflow.
  • Tier-size propagation: the map editor must detect lots whose rectangle footprint does not match their current tier dimensions and provide a draft action to sync/apply those tier sizes. Applying or syncing a tier resizes affected lots in draft/preview semantics. If this causes overlaps or lots outside their block, the editor shows conflicts and blocks Publish until resolved.
  • Draft safety: conflicts are allowed while editing. Publish is blocked when overlaps or outside-block violations remain.
  • Existing current worktree: the prior Align Layout foundation in this worktree is the starting point, including AlignLayoutPanel.tsx and geometry-transform.ts. Execution must not discard that work.

Product Model

Guided Setup Steps

  • Map reference: view controls for mock/default/satellite-style background, pan, zoom, rotate view indicator if already available, and reset north. View only.
  • Site Plan: upload/select image, show/hide, opacity, lock, move, resize, rotate, and compare against the base map.
  • Blocks: create/select rectangle blocks, move, resize width, resize height, rotate, and set block-local grid orientation.
  • Lots: generate rows/columns/count, arrange lots inside selected block, move sold/occupied lots only inside the same block, and keep cross-block reassignment explicit.
  • Tiers: assign tier visually by individual lot, multi-select, and paintbrush-style assignment; tier size is displayed as real-world footprint and existing lots can be synced to current tier dimensions in draft.
  • Review: publish review lists created placeholders, moved available lots, moved protected lots, tier changes, tier-size impacts, overlaps, and outside-block conflicts.

Interaction Rules

  • Only the active layer is directly editable. Other layers stay visible but locked or ghosted.
  • Direct handles must be visible on selected site plan, block, and lot/group frames.
  • Rows, columns, count, gap, orientation, and default tier are configured from the selected block context.
  • Tier paint mode must not accidentally start geometry drag. Geometry mode must not accidentally paint tiers.
  • Conflicts are highlighted on the canvas and listed in the side panel with actions to select, fix, or cancel.

Constraints

Must

  • Keep initial geometry rectangle-only for blocks and lots.
  • Keep all edits draft-only until Publish.
  • Allow sold/occupied lot geometry movement only inside the same block.
  • Preserve sold/occupied lot identity and business data during visual geometry edits.
  • Require explicit reassignment for any cross-block lot movement.
  • Generate available placeholder lots automatically from grid settings and allow manual exact count control.
  • Use tier widthM/lengthM as the authoritative lot footprint.
  • Detect overlaps and lots outside their block after geometry, grid, lot, and tier-size edits.
  • Block Publish while invalid geometry remains.
  • Keep existing protected-lot safeguards for delete, reassign, status, renumber, and other inventory operations.
  • Run the execution loop task-by-task, with focused checks after each task and full verification at the end.

Must Not

  • Do not implement real Google Maps, paid APIs, geospatial projection calibration, or legal survey support.
  • Do not implement arbitrary polygon blocks or non-rectangular lots in this execution.
  • Do not silently reassign lots to another block through dragging.
  • Do not delete, renumber, recode, sell, unsell, hold, release, or alter client/contract/burial data from geometry movement.
  • Do not add new dependencies or drag libraries.
  • Do not edit frozen @/domain constants beyond consuming existing tier fields.
  • Do not remove existing Advanced Inventory capabilities.
  • Do not bypass route blockers, dirty state, undo/redo, publish/discard, or validation behavior.

Out Of Scope

  • Database schema changes or backend persistence.
  • Real Google Maps integration, API keys, or external network map providers beyond existing/mock base layers.
  • Four-corner image warp, perspective correction, survey coordinate systems, or GPS anchoring.
  • Arbitrary polygon blocks, freeform lots, curved paths, aisles, and irregular cemetery sections.
  • Sales, payments, burials, client records, or pricing book money changes.
  • Mobile-first redesign. The editor remains desktop/tablet oriented, but must not break narrow viewport layout.

Risk

Level: 4 - Major Impact. This changes the core admin workflow for cemetery geometry and how tier dimensions affect existing lot shapes.

Risks Identified

  • Geometry correction can be mistaken for inventory mutation. Mitigation: mode-based editing, active-layer locks, explicit copy, and publish review groups separating visual moves from reassignment/status/tier changes.
  • Tier-size propagation can create layout conflicts across many lots. Mitigation: apply geometry sync in map-editor draft/preview semantics, detect overlaps/outside-block violations, show counts, and block Publish until fixed.
  • Sold/occupied lots may be moved visually. Mitigation: only allow same-block geometry movement; preserve IDs, numbers, block, tier, status, clients, contracts, payments, burials, capacity, notes, and prices.
  • Rectangle-only MVP could be confused with final arbitrary-shape support. Mitigation: label rectangle-only scope in the spec and keep future polygon support out of execution.
  • Pointer interactions can make EditorSurface.tsx unmaintainable. Mitigation: keep heavy geometry and validation in helpers, with the surface responsible for event wiring and visual state.
  • Publish blocking can frustrate admins if conflicts are hard to find. Mitigation: canvas highlights, side-panel conflict list, select/focus actions, and clear repair/cancel paths.
  • Pricing tier copy currently conflicts with this behavior. Mitigation: update tier dimension wording and confirmation so admins understand existing map layouts may need review when dimensions change.

Blast radius: /map-editor, map-editor draft store, grid generation helpers, geometry transform helpers, publish dialog/reporting, tier editor copy/store behavior, pricing tier consumers, live map geometry after Publish, audit summaries, QA scripts, and existing mock validation.

Pushback

  • "Drag, drop, resize everything" is not a safe execution contract. The correct contract is layered editing with only one active layer editable at a time.
  • "Tier size always controls lot size" is cleaner than "only new lots unless something overlaps." The latter creates hidden exceptions admins cannot reason about.
  • Real maps and arbitrary shapes do not belong in this execution. Future-us will hate mixing API/geospatial integration into a core editor rewrite before rectangle behavior is stable.

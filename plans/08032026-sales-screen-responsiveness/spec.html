Why

The /sales route is a desktop-first operational surface inside a fixed-width application rail. At narrow widths, the shell consumes space the page cannot recover, filters retain desktop minimum widths, tables expose up to twelve columns through horizontal scrolling, and transactional overlays retain desktop composition.

Agents and managers need fast lookup, contract details, hold requests, and payment posting on phones. Shrinking the desktop layout would make those tasks technically visible but operationally poor. The route needs responsive recomposition while the existing desktop density, calculations, permissions, and workflows remain intact.

What

Build a responsive presentation contract for the complete sales surface: the route header, metrics, four tab views, filters, records, detail sheets, creation flows, payment and hold workflows, invoice preview, secondary dialogs, and supporting sales controls.

Add only the shared shell behavior required to let /sales occupy a mobile viewport. Keep existing data sources and finance helpers authoritative. Desktop keeps its tables and information density; mobile gets task-prioritized record layouts and viewport-safe overlays.

Primary mobile jobs

  1. Find a contract, payment, receivable, or client quickly.
  2. Open the relevant contract or client details.
  3. Request a lot hold without viewport or keyboard obstruction.
  4. Post a payment and review its schedule, balance, trust-fund, and commission effects.

Secondary mobile jobs

  • Create contracts and clients.
  • Review owner-level metrics and oversight details.
  • Print or inspect invoices.
  • Transfer, cancel, or void records when permissions allow.

Responsive and UX contract

Viewport tiers

  • 320–639px: mobile shell, stacked page header, compact two-column metrics, two-column tab grid, visible search, filter sheet, mobile record lists, and viewport-filling transactional overlays.
  • 640–767px: wider mobile composition with the same navigation and record strategy; forms may use two columns only when labels and values fit without truncation.
  • 768–1023px: retain the mobile shell, compact filters, and responsive record presentations. Execution confirmed that returning the 232px rail at 768px leaves insufficient operational width; the rail and tables return together at 1024px.
  • 1024px and above: preserve current desktop tables, filters, hierarchy, and density unless an accessibility correction is explicitly listed.

Main sales surface

  • Keep the page title and permitted actions visible without horizontal scrolling. Stack actions at very narrow widths and keep the primary action first.
  • Render summary values as a compact, scannable grid on mobile. Secondary hints may collapse visually but must remain available where they affect interpretation.
  • Keep all four tabs discoverable. Use a full-width two-column tab arrangement at the narrowest tier and the existing single-row treatment when space permits.
  • Keep search outside the filter overlay. Put secondary filters in one labeled sheet with active-count text, clear, cancel, and apply/close behavior.
  • Desktop tables remain authoritative presentations of dense data. Mobile record layouts use the same filtered row objects and formatting helpers.
  • Mobile records prioritize identity, financial state, health/status, and the next useful action. They must not duplicate business calculations.

Mobile record priorities

  • Contract: buyer and contract number; lot; balance and payment health; contract status; then terms, agent, and signed date.
  • Payment: official receipt number and buyer; date; amount and posting status; then method, contract, trust fund, and receiver.
  • Receivable: buyer and severity; outstanding amount; days past due and next due; then last payment and permitted actions.
  • Client: name and reference; city; outstanding amount and contract count; then senior status and total contracted.

Overlay and form behavior

  • Sales sheets occupy the full mobile width. Long dialog flows use dynamic viewport height, one scrolling content region, safe-area padding, and a persistent action footer.
  • Comboboxes, calendars, selects, and dropdowns must remain within the visual viewport and align to their triggers without a fixed 320px floor.
  • The contract stepper remains understandable at 320px. Labels may shorten visually, but step identity and current state remain exposed.
  • The invoice screen preview may reflow for mobile, but print-specific A4 output must not change.
  • On-screen keyboards must not hide the focused field, validation message, or required submit/cancel controls.

Anti-slop direction

  • Do not turn every record into a decorative card with repeated borders and shadows. Use restrained list rows and grouping that reflect operational priority.
  • Do not add gradients, glass effects, oversized radii, new colors, decorative motion, or generic dashboard ornaments.
  • Do not hide essential finance, status, or identity data merely to make a screenshot look clean.
  • Motion supports orientation only. Existing reduced-motion behavior remains authoritative.

Accessibility contract

Goal: WCAG 2.2 A/AA-oriented operation of lookup, detail, hold, payment, creation, and secondary sales flows across touch, keyboard, zoom, and reduced-motion contexts. This is practical engineering guidance, not legal certification.

  • Use semantic lists for mobile records. Do not nest buttons. When a row also has actions, expose a separate named detail control.
  • Sortable desktop headers use real buttons and expose aria-sort on the owning column header. Keyboard activation must match pointer sorting.
  • The mobile navigation and filter surface require an accessible name, focus containment through the existing primitive, Escape dismissal, trigger focus return, and visible focus.
  • Tabs retain Radix keyboard behavior, a clear selected state, logical DOM order, and non-color-only state communication.
  • Primary mobile actions target at least 44px where layout permits. Every control must meet the WCAG 2.2 24px minimum or a valid spacing exception.
  • Icon-only controls retain explicit accessible names. Badge, health, status, and overdue meaning must not rely on color alone.
  • Labels, helper text, required state, invalid state, and errors remain programmatically associated after responsive rearrangement.
  • Nested dialog flows, including new-client creation from a combobox, must return focus to the invoking control and avoid competing traps.
  • At 200% zoom, content reflows without two-dimensional page scrolling, clipped controls, or loss of information.
  • Automated checks are signals only. Manual keyboard, focus, zoom, on-screen keyboard, and assistive-name checks remain required.

  • No native replacement controls where shadcn/Radix primitives already exist.
  • No global responsive redesign of unrelated routes.

  • No mobile implementation that depends only on horizontal table scrolling.
  • No edits to src/index.css, which is not imported by the application entrypoint.

Out of scope

  • Redesigning non-sales page content.

  • Performance optimization unrelated to responsive rendering.
  • Refactoring generic UI primitives unless a listed sales requirement cannot be met locally.

Risk

Level: 3 — Structural Risk, discussed and mitigated. The shell change affects every authenticated route even though the feature scope is sales.

Risks and mitigations

  • Shared shell regression. A mobile-only sales navigation bypass would introduce architectural drift. Mitigation: reuse one extracted permission-aware navigation renderer in the desktop rail and mobile sheet; leave desktop rail persistence and width unchanged.
  • Desktop/mobile presentation drift. Separate markup can disagree about finance or status. Mitigation: both presentations consume the same filtered row objects and existing formatters; presenters do not calculate.
  • Shared DataTable blast radius. Sort semantics affect every consumer. Mitigation: restrict the edit to semantic buttons, aria-sort, keyboard activation, and unchanged visual styling; regression-check all consumers.
  • Nested focus and viewport failure. Dialogs, sheets, popovers, and calendars can trap focus or escape the viewport. Mitigation: retain Radix primitives, apply local viewport constraints, and verify focus return and keyboard visibility for nested client creation.
  • Mobile card overload. Repeating every desktop column would recreate the table vertically. Mitigation: enforce the record priorities in this spec and move secondary data below the primary scan line.
  • Print regression. Reflowing the invoice preview can affect A4 output. Mitigation: change screen-only classes and retain the existing scoped print stylesheet.
  • Stale branch base. Local main trails origin/main. Mitigation: execution reports the current divergence before code changes; any merge or rebase needs an explicit user command.
  • QA portability. Existing browser scripts assume a Mac Chrome path and fixed port. Mitigation: the focused runner accepts BASE_URL and CHROME_PATH, reuses Puppeteer Core, and adds no dependency.

Blast radius

  • AppShell: /map, /dashboard, /sales, /burials, /agents, /approvals, /pricing, /map-editor, and /audit.
  • DataTable: lot ledger, agent detail, commissions, services, payouts, earnings, roster, interments, sales, and approval history consumers.
  • Sales comboboxes: contract builder, hold request, ownership transfer, and nested client creation.
  • Sales finance displays: contract builder, contract detail, hold, payment preview, and invoice-related views.

Alternatives considered

  • A — Recommended: one responsive shell path, sales-local mobile presenters, and minimal shared sort semantics.
  • B — Rejected: keep the rail and add more horizontal scrolling. This fails the 320px goal.
  • C — Rejected: fork shared tables and navigation inside /sales. Future-us would maintain two permission and interaction systems.
  • D — Deferred: redesign every application route for mobile. That expands beyond the approved sales scope.

Rollback boundary

Keep each task independently reviewable. If a shared shell or table change regresses unrelated routes, revert that task without discarding sales-local presenters. If mobile presenters drift from desktop data, stop and reconcile the shared row model before continuing.
